# 온라인 통신·재접속 제안과 연결 실험

2026-11-06. 기준 커밋 `474ca1a`의 [기획](game-spec.md), [규칙 모델](game-rules-design.md), [온라인 협업](online-collaboration.md), [UI 경계](design-system.md)를 읽고 작성했다. 아래는 검토용 초안이며 제품 라이브러리·호스팅·DB·게임 규칙을 확정하지 않는다.

## 제안 요약

서버가 방과 대국의 단일 권위를 갖고 방마다 명령을 순차 처리한다. 클라이언트는 의도만 전송하고 서버가 공통 TypeScript 규칙을 호출한다. 처음에는 변경 후와 재접속 때 플레이어별 전체 스냅샷을 보내 정합성을 우선 검증한다. 이벤트 차분·누락 재전송은 필요성이 확인되면 도입한다.

기본 대국은 확정된 2인·15×15·정확히 5목/6목을 따른다. 통신 실험은 판·착수·승리 판정을 전혀 구현하지 않으며, 기존 화면과 디자인 시스템도 수정하지 않는다.

## 통신과 실행 환경 선택지

| 선택지 | 이 프로젝트에 주는 이점 | 영향과 검토할 점 |
| --- | --- | --- |
| 브라우저 표준 WebSocket + Node 서버 `ws` | 작은 전송 계층, JSON 계약과 규칙 호출을 직접 제어. 다른 호스트로 옮기기 쉬운 출발점 | 방·인증·heartbeat·백오프·스냅샷 복구·중복 처리를 애플리케이션에서 구현 |
| Socket.IO 클라이언트·서버 | 방, ack, 재연결과 선택적 연결 상태 복구 기능 활용 | 전용 클라이언트/프로토콜 도입. 복구 실패 시 스냅샷은 여전히 필요하고 기본 전달 보장은 중복 없는 적용을 보장하지 않음 |
| Workers + Durable Objects | 방 하나를 객체 하나에 대응시키는 관리형 실행·상태 모델 검토 가능, WebSocket hibernation 지원 | 객체 수명·영속 저장·비동기 처리 규율에 맞춘 어댑터 필요. 휴면 중 상태 복원과 명령 직렬화 검증, 플랫폼 종속성 고려 |
| 관리형 메시지 중계 + 별도 권위 서버 | 예: Supabase의 Auth·채널 권한·데이터 저장 활용 검토 가능 | 채널 접근 제어는 게임 명령 검증과 다름. 공통 TS 규칙 실행 주체가 별도로 필요하며 비공개 정보를 방 전체에 보내면 안 됨 |

공식 자료: [ws](https://github.com/websockets/ws), [Socket.IO 복구](https://socket.io/docs/v4/connection-state-recovery/), [전달 보장](https://socket.io/docs/v4/delivery-guarantees/), [Durable Objects WebSocket](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), [Supabase 채널 권한](https://supabase.com/docs/guides/realtime/authorization).

Node 서버 호스팅 후보로 Render 같은 WebSocket 지원 웹 서비스를 비교할 수 있다. Render는 연결 최대 시간을 강제하지 않지만 인스턴스 종료·네트워크 장애 시 끊김을 처리해야 한다([공식 문서](https://render.com/docs/websocket)). Node 호스팅은 배포 이동성이 장점이지만 다중 인스턴스에서 방 소유권·공유 상태·재시작 복구를 설계해야 한다. Durable Objects는 방별 실행 모델을 활용할 수 있지만 어댑터와 플랫폼 전용 운영 지식이 필요하다. 현재 특정 서비스를 생성하거나 배포하지 않았다.

비용은 단정하지 않는다. 예상 동시 방/연결 수, 대국 시간, idle 비율, 메시지 빈도·크기, 지역 지연, 저장량·보존 기간, 재시작 복구 목표를 받은 뒤 각 서비스의 현재 요금·제한으로 비교해야 한다. 관리형 중계에 더해 권위 서버까지 운영하면 두 경로의 비용과 장애 지점이 생긴다.

## 서버가 관리할 상태

| 범위 | 내용 | 클라이언트 공개 범위 |
| --- | --- | --- |
| 방 | roomId, 참가 권한, 2인 자리 배정, 준비·시작 상태, 활성 gameId, 방 수명 | 권한 있는 멤버의 공개 요약. 초대/인증 비밀 제외 |
| 연결·신원 | 인증/게스트 세션 → playerId, 현재 소켓, 세대, 접속 여부, 마지막 생존 확인, 재접속 유효 기간 | 본인의 복구 수단과 필요한 상대 접속 여부만 |
| 대국 | 전체 GameState, 게임 revision, 모드·규칙 버전, 선공 순서와 직전 대국 순서 | 플레이어별 투영 상태만 |
| 비공개 데이터 | 손패, 지뢰, 은신, 난수 상태, 미공개 선택지 등 | 기획이 허용한 필드만. 공개 범위 미정이면 전송하지 않음 |
| 처리·복구 | 방별 명령 큐, 처리 결과/중복 키, 저장 체크포인트, 확정된 응답 창과 deadline | 요청 결과, 허용된 응답 기회/시간만 |

최소 실험은 방 ID·멤버·접속 여부·방 revision·메모리 토큰만 갖는다. 멤버는 게임 자리나 playerId로 확정한 모델이 아니다. 제품의 방 생성·초대·2인 정원·재대국 권한은 다음 계약에서 분리한다.

## 공통 TypeScript 규칙 호출 경계

실제 규칙 코드는 아직 저장소에 없다. 별도 서버용 승리 판정이나 카드 구현을 만들지 않는다. 2단계 담당자가 만드는 단일 모듈을 로컬 세션과 서버 어댑터가 함께 import하도록 제안한다. 우선 `src/entities/game/model` 같은 독립 모듈로 두고, 별도 빌드/배포가 필요해질 때 `packages/game-rules` 분리를 검토한다. 위치는 담당자와 합의한다.

1. 규칙: 현재 모델의 `startGame(mode, playerIds)`, `applyCommand(state, command)`를 유지한다. React·소켓·DB·실시간 시계를 import하지 않는다. 장목·턴·카드 지급·효과·방어 응답 등 상태 전이는 모두 이 한 모듈에서 처리한다.
2. 세션: 인증된 연결에서 actorId를 정하고 wire 입력을 규칙 명령으로 변환한다. 클라이언트가 보낸 actorId·판·승자·난수 결과는 신뢰하지 않는다. 구조와 크기는 전송 계층, 합법 행동은 공통 규칙에서 검증한다.
3. 공개 상태: `projectForPlayer(fullState, playerId)` 같은 순수 투영 함수를 한곳에 두고 서버가 매 송신·재접속에 호출한다. 전체 상태를 직렬화한 뒤 UI에서 숨기는 방식은 금지한다. 규칙 이벤트에도 비공개 정보가 있을 수 있어 원본 이벤트는 방송하지 않는다. 스냅샷과 오류·로그·재전송 경로 모두 같은 원칙을 따른다.
4. 원자적 전이: 성공한 상태, 갱신된 난수, 지급 결과, revision, 요청 처리 기록을 함께 확정한다. 복구 시 `startGame`이나 턴 시작 이벤트를 다시 실행하지 않는다. 이벤트를 읽어 카드를 다시 지급하지 않는다.
5. 확장: 응답 제한 시간이 확정되면 서버가 응답 창 ID를 붙인 시스템 명령을 전달하고 규칙이 해당 창의 유효성을 검사한다. 난수 상태는 규칙 입력/결과로 재현 가능하게 관리하되 서버에만 둔다. 미확정 효과의 순서는 구현하지 않는다.

컴파일 가능한 범용 호출 포트와 메시지 타입 초안은 [contracts.ts](../experiments/websocket/contracts.ts)에 두었다. 규칙의 구체 타입을 다시 정의하지 않고 제네릭으로 받는다. 이 파일은 제품 공개 API가 아니며 런타임 실험에 게임 규칙을 연결한 상태도 아니다.

## 메시지 계약 초안

JSON, `v: 1`. 클라이언트 요청은 `requestId`를 포함한다. 타입 검사 외에 서버 런타임 스키마 검증이 필요하다. 게임 ID는 재대국마다 새로 발급한다.

| 방향 | type | 주요 필드와 의미 |
| --- | --- | --- |
| C → S | room.join | requestId, roomId. 제품은 별도 인증·방 참가 권한 필요 |
| C → S | session.resume | requestId, roomId, resumeToken. 기존 신원 복구 요청 |
| S → 본인 | session.ready | requestId, memberId, resumeToken. 실험용 이름이며 제품의 playerId/인증 계약과 합의 필요 |
| C → S | ping | requestId. 실험의 애플리케이션 메시지이며 자동 heartbeat 아님 |
| S → 본인 | pong / error | requestId, 오류라면 code. 잘못된 입력은 requestId가 없을 수 있음 |
| S → 방 | room.snapshot | roomId, revision, 공개 멤버 접속 상태. 실험은 이 스냅샷만 구현 |
| C → S | game.command | requestId, roomId, gameId, expectedRevision, action. actorId는 서버에서 결합 |
| S → 본인 | command.result | requestId, gameId, revision, result: {ok:true} 또는 {ok:false,code} |
| C → S | state.sync | requestId, roomId, gameId. 현재 허용 스냅샷 재요청 |
| S → 본인 | game.snapshot | roomId, gameId, revision, view. 플레이어별로 생성 |

게임 명령 예시(미구현):

```json
{"v":1,"type":"game.command","requestId":"cmd-123","roomId":"r1","gameId":"g1","expectedRevision":7,"action":{"type":"place-stone","position":{"row":7,"column":7}}}
```

게임 revision은 승인된 규칙 전이에만 증가한다. 접속 상태는 별도 room revision으로 관리해 네트워크 흔들림이 정상 착수를 stale로 만들지 않게 제안한다. 응답 창 전이도 게임 revision을 증가시킨다. 클라이언트는 같은 gameId에서 더 오래된 스냅샷을 덮어쓰지 않고, 새 gameId는 별도 흐름으로 취급한다.

방별 직렬 처리 순서는 **신원·권한 → 요청 ID 중복 조회 → 기준 revision 확인 → 공통 규칙 → 원자적 저장 → 응답/플레이어별 스냅샷**이다. 중복 키는 `(gameId, playerId, requestId)`이고 정규화한 원래 입력과 결과를 함께 보관한다. 같은 ID·같은 입력은 기존 결과를 반환하며 재적용하지 않는다. 같은 ID·다른 입력은 `REQUEST_ID_REUSED`, 다른 ID의 오래된 기준은 `STALE_REVISION`으로 거부한다. 미승인 명령은 상태·난수·카드 지급을 바꾸지 않는다.

동시 착수는 큐 안에서 한 번씩 처리하며, 다중 프로세스에서는 단일 방 소유자 또는 저장소 트랜잭션/CAS로 같은 보장을 유지해야 한다. ack 유실 시 같은 ID로 재시도하고 재접속 후 스냅샷으로 조정한다. 중복 기록 수명은 복구 보장 기간 이상으로 유지해야 하며 만료 뒤에는 같은 보장을 주장하지 않는다. 오류 상세에 비공개 값이나 내부 스택을 넣지 않는다.

## 재접속과 상태 저장 선택

첫 제안은 전체 스냅샷 복구다. 브라우저는 `connecting → joined → reconnecting → syncing → joined` 상태를 표시하고 복구 완료 전 게임 입력을 막는다. 자동 재시도는 지수 백오프·jitter와 상한을 두고, 인증 거부/만료 시 무한 재시도를 멈춘다. 확정 여부가 모호한 명령은 새 ID로 보내지 않는다. 자동 재시도 UI와 로직은 이번 실험 범위 밖이다.

제품에서는 WSS, Origin 허용 목록, 세션/방 권한, 스키마·메시지 크기·빈도 제한을 적용한다. 서버 ping/pong 또는 합의한 heartbeat로 반쯤 끊긴 연결을 감지한다. 재접속 토큰은 로그·URL에 넣지 않고 서버에는 해시와 만료를 보관하며, 회전/재사용 처리와 저장 위치는 계정 선택에 맞춰 정한다. 현재 활성 연결을 거부할지, 새 연결로 교체하며 이전 연결을 fencing할지 선택해야 한다. 실험은 활성 연결 거부만 구현한다.

| 복구 목표 | 저장 선택지와 영향 |
| --- | --- |
| 동일 프로세스에서 잠깐 끊김 복구 | 메모리로 시작 가능. 재시작·배포 시 방/신원/중복 기록 소실을 명시해야 함. 이번 실험 범위 |
| 서버 재시작 후 대국 복구 | 상태·규칙 버전·난수·처리 기록을 원자적으로 영속 저장. PostgreSQL 트랜잭션 또는 방별 플랫폼 저장을 비교 |
| 여러 인스턴스와 장애 복구 | 방 소유권/세대, 원자적 revision 갱신, 저장 기록, 라우팅과 복구 전략 필요. Redis를 도입하더라도 Pub/Sub만으로 영속 복구를 대체하지 않음 |

DB는 아직 추가하지 않았다. 계정/전적/진행 중 대국의 보존 요구가 나오기 전에는 테이블과 공급자를 확정하지 않는다. 방 유예 기간과 연결 상태는 기술 정책이고, 접속 종료 시 패배·턴 정지·방어 미응답 처리는 게임 정책이므로 분리한다.

## 이번 실험의 결과와 다음 합의

[독립 실험](../experiments/websocket/README.md)은 `ws`를 자체 package/lockfile에만 설치했다. 표준 WebSocket 클라이언트 여러 개가 실제 loopback 서버와 통신해 방 공유·격리, 접속 종료 후 누락된 멤버 상태 복구, 동일 신원, 잘못된/만료된/다른 방 토큰, 활성 연결 충돌, 잘못된 메시지 거부를 검증한다. 게임 처리·비밀 상태 투영·명령 중복/경쟁·heartbeat·자동 백오프·영속 복구는 미구현이다. 실험의 60초 유예와 멤버 정원은 게임 규칙이 아니다.

다음 단계에서 함께 결정할 질문:

1. 게스트 초대방부터 시작할지, 계정이 필요한지? 재접속은 같은 탭만인지 새로고침/다른 기기도 지원할지? 활성 연결 교체 정책과 토큰 보관 방식에 영향이 있다.
2. 배포·서버 재시작 후에도 진행 중 대국을 복구해야 하는지? 이에 따라 메모리 실험에서 영속 저장으로 넘어가는 시점이 달라진다.
3. 운영 최소화를 우선한 방별 관리형 실행과 Node 호스팅 중 무엇을 비교할지? 예상 규모·예산·지역을 받은 뒤 비용 비교한다.
4. 규칙 담당자의 실제 모듈 경로/API와 플레이어별 투영 책임을 합의할 수 있는지? 이후 기본 착수만 연결하는 수직 단면을 만든다.
5. 방어 응답 창·미응답/접속 종료·증강 지급 라운드·무작위 풀·비공개 정보 공개 시점은 기획 결정이 필요하다. 연결 실험은 이 결정을 선점하지 않는다.
