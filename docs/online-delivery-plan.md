# 인터넷 온라인 대국 완성을 위한 가이드라인

2026-11-07 기준 제안이다. 사용자 요청은 기존 게임과 화면을 유지하면서 실제 온라인 2인 대국에 집중하는 것이다. 이 문서는 앞으로의 구현·배포 순서와 완료 기준이며, 서비스 생성·요금제·DB 계약을 확정하거나 실제 배포한 기록은 아니다.

## 현재 위치

- `server/index.mjs`에 Node 24 + ws 백엔드가 있으며 공통 TypeScript 규칙을 호출한다. `dist` 화면과 `/online` 소켓을 같은 HTTP 서버가 제공한다.
- 로컬에서 기본/스킬 테스트 대국·방·재접속을 연결했다. 이전 검증은 자동 테스트 34개와 같은 PC의 두 브라우저 탭이다. 인터넷상의 서로 다른 두 기기 검증과 공개 배포는 아직 하지 않았다.
- 방·토큰·게임·중복 요청 기록은 프로세스 메모리에만 있다. 서버 재시작/새 버전 배포 후 대국은 복구되지 않는다.
- 현재 온라인 변경은 로컬 기능 브랜치의 미커밋 작업이다. GitHub main만 배포하면 이 구현이 포함되지 않을 수 있다.

## 목표와 범위

첫 목표는 **공개 HTTPS URL을 PC와 휴대폰 등 서로 다른 기기·네트워크에서 열어 같은 방의 대국을 끝내는 것**이다. 두 번째 목표는 끊김·응답 유실·서버 재시작에도 승인된 행동을 잃거나 중복 적용하지 않는 것이다. 두 완료 기준을 따로 보고한다.

기존 로컬 대국·5목/6목·스킬 테스트·디자인 미리보기를 유지한다. 새 카드·증강·랭킹·매칭·소셜 로그인·UI 재설계는 이번 온라인 작업의 범위 밖이다. 계정 없이 게스트 초대방으로 검증할 수 있다. 방어 시간·접속 종료 패배 등 미확정 게임 규칙은 통신 개발 과정에서 정하지 않는다.

## 1. 배포할 버전을 재현 가능하게 준비

1. 현재 변경과 로컬 작업을 확인하고 목적별 커밋/PR로 공유할 기준 SHA를 만든다. 배포는 그 SHA를 기준으로 한다.
2. 깨끗한 체크아웃에서 `npm ci`, `npm run lint`, `npm test`, `npm run build`를 실행한다. Node 24를 고정하고 현재 CI를 통과시킨다.
3. 빌드 후 `npm run server`만으로 화면, `/health`, `/online`이 동작하는지 확인한다. 프로덕션 실행에 Vite 개발 서버가 필요하면 안 된다.
4. health 응답/서버 시작 로그에 배포 버전 식별자를 추가하되 토큰과 비공개 상태는 기록하지 않는다.

완료: 다른 환경에서 같은 버전으로 테스트·빌드·서버 시작을 재현할 수 있다.

## 2. 단일 서버로 공개 시험 배포

현재 코드를 가장 적게 바꾸는 제안은 **Node Web Service 한 개에 화면과 WebSocket을 함께 배포**하는 것이다. Render는 가능한 후보이며 라이브러리와 호스팅을 다시 설계하는 일을 첫 단계의 선행 조건으로 삼지 않는다. 다른 호스트를 선택하더라도 Node 24, 장기 WebSocket, HTTPS/WSS, 환경변수 PORT, health check와 종료 신호 처리를 지원하는지 확인한다.

Render를 선택할 경우의 설정 예:

| 설정 | 값/처리 |
| --- | --- |
| 서비스 | Node Web Service, 처음에는 단일 인스턴스 |
| 소스 | 온라인 구현이 포함된 승인된 브랜치/커밋 |
| 빌드 | `npm ci && npm run build` |
| 시작 | `npm run server` |
| Node | `.nvmrc`의 24 또는 검증한 정확한 24.x 버전 |
| HOST | `0.0.0.0` |
| PORT | 호스트가 제공하는 환경변수 사용 |
| 상태 확인 | `/health` |
| 화면/소켓 | 같은 공개 Origin, `https://<호스트>/`와 `wss://<호스트>/online` |
| Origin | 실제 공개 화면의 정확한 Origin을 허용. 프록시 Host 전달을 실제 handshake로 확인 |
| 배포 방식 | 메모리 버전 시험 중에는 수동 배포, 지속적인 대국 복구 후 CI 통과 시 배포 검토 |

Render는 WebSocket과 TLS 종료를 지원하며 외부 연결을 받으려면 `0.0.0.0`으로 바인딩해야 한다. Free 서비스는 idle 시 중지되거나 재시작될 수 있으므로 시험용과 지속 운영용의 요구를 구분해 요금제를 선택한다. 유료 단일 서버도 메모리 상태의 재시작 복구를 보장하지는 않는다. 플랫폼의 무중단 HTTP 배포가 진행 중 게임 상태까지 승계해 주지는 않는다.

완료: 공개 URL에서 화면과 `/health`가 열리고 `/online` handshake가 101로 성공한다. localhost·개발 서버·로컬 터널만 확인한 결과를 인터넷 배포 완료로 보고하지 않는다.

## 3. 실제 두 기기로 대국 완료

PC의 Wi-Fi와 휴대폰의 셀룰러처럼 서로 다른 네트워크를 사용한다. 두 탭만으로 이 단계를 대체하지 않는다.

1. A가 5목 기본 방 생성 → B가 코드 참가 → 동일 판과 차례 확인 → 승리까지 진행 → 둘 다 재대국 동의 → 선공 교대 확인.
2. 6목 모드와 기존 스킬 테스트에서 카드 사용 → 상대 방어 → 원래 턴 재개 → 착수를 확인한다.
3. 한쪽 새로고침, 잠시 네트워크 차단 후 복구, 모바일 백그라운드 복귀를 확인한다. 복구 중 입력을 막고 같은 자리·판·본인 손패를 복구해야 한다.
4. 끊김 직전에 보낸 명령의 ack가 유실된 경우 같은 requestId 재전송으로 한 번만 적용되는지 확인한다.
5. 세 번째 참가 거부, 상대 차례의 행동 거부, 다른 사람의 손패/난수/덱 정보가 응답에 없는지 확인한다.

완료: 배포 SHA·공개 URL·두 기기의 브라우저·검증 시나리오와 결과를 남긴다. 이 시점은 '인터넷 시험 대국 가능'이며 서버 재시작 복구 완료와 구분한다.

## 4. 안정적인 대국 복구를 위한 저장 경계

서버 배포/재시작 때 대국을 계속할 요구가 있으면 영속 저장이 필요하다. 이 요구를 충족할 후보로 관리형 PostgreSQL을 제안하되 DB 공급자와 비용은 선택 전에 검토한다. 계정/랭킹 기능을 동시에 만들 필요는 없다.

최소 저장 대상은 방/멤버, 복구 토큰의 해시·유효 기간, 전체 게임 상태·규칙 버전·난수 상태, gameId/revision, 요청 ID·입력 지문·처리 결과와 대국 종료 상태다. 비공개 전체 상태는 서버만 읽고 전송은 기존 플레이어별 투영을 거친다.

처리는 **방/대국 잠금 → 인증·권한 → 기존 요청 결과 조회 → revision 검사 → 기존 TS 규칙 호출 → 상태와 요청 결과의 동일 트랜잭션 저장 → commit → 응답** 순서로 만든다. 저장 실패 시 승인 ack를 보내지 않는다. 카드 지급과 난수 갱신도 같은 상태에 포함한다. 게임 판정 코드를 SQL이나 다른 서버 모듈에 복제하지 않는다.

현재 동기 메모리 처리에 비동기 DB를 추가하면 요청이 교차 실행될 수 있다. 방별 큐와 DB 트랜잭션/CAS 등으로 직렬화 경계를 유지한다. 복구는 저장 상태를 읽어 투영하며 `startGame`과 턴 시작 지급을 다시 실행하지 않는다.

완료: 행동 승인 후 프로세스를 강제 종료해도 두 클라이언트가 재접속해 동일한 revision/판/손패를 받는다. 같은 요청을 재전송해도 착수·카드 지급·공격이 중복되지 않는다. 영속 저장 도입 전 인스턴스를 여러 개로 늘리지 않는다.

## 5. 장애·배포·운영 흐름 완성

- ack 대기 시간 초과와 snapshot 동기화를 명시적으로 처리한다. 현재 클라이언트는 결과를 기다리는 동안 재연결이 없으면 대기가 길어질 수 있으므로 제한 시간 후 같은 ID 조회/재전송 정책을 추가한다.
- 대기방, 한 명만 장시간 남은 방, 종료 방의 수명과 세션 만료를 설정한다. 기술적 정리와 패배/방어 미응답 게임 정책을 분리한다.
- 메시지 스키마를 한곳에서 검증하고, handshake·미참가 소켓·IP/세션별 연결/방 생성 제한을 추가한다. 현재 JSON 파싱 실패 경로도 요청 제한에 포함시킨다.
- 종료 신호에서는 새 방/명령 수락을 멈추고 확정 상태를 저장한 뒤 재접속 가능한 종료를 알린다. 현재 방 파기·토큰 삭제와 재시작을 위한 종료를 구분한다.
- 접속 수·활성 방·ack 지연·재접속 성공/실패·거부 사유·예외를 수집한다. 토큰·전체 손패/게임 비공개 상태는 로그에서 제외한다.
- 동일 프로세스/새 프로세스 복구, 동시 요청, 중복 요청, 재접속 직후 스냅샷, 토큰 만료·구 연결 차단을 CI/배포 후 검사에 포함한다.
- 메모리 상한과 송신 대기 버퍼를 감시하고 부하 테스트 결과로 제한을 정한다. 목표 동시 방 수·지역·예산이 나오기 전 다중 서버나 Redis를 선행 도입하지 않는다.

완료: 시험 중 재시작·배포·끊김을 구분해 사용자에게 안내하고, 서버 복구 목표에 맞는 결과를 확인한다. 서버 버전 변경 시 저장 상태/규칙 버전 호환성과 롤백 가능 여부도 검사한다.

## 다음 구현의 권장 순서

**배포 버전 준비 → 공개 시험 배포 → 두 기기 대국 → 저장과 재시작 복구 → 배포/장애 검증** 순서다. 각 단계마다 실제로 통과한 완료 기준만 보고한다. 배포 계정·요금제·공개 URL이나 DB 선택이 필요한 지점에서는 구체적인 설정과 비용 영향을 먼저 제시한다.
