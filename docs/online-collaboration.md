# 온라인 구현 협업 가이드

2026-11-06 기준 제안. 게임 기획은 [game-spec.md](game-spec.md), 규칙 경계의 현재 초안은 [game-rules-design.md](game-rules-design.md), 전체 순서는 [development-roadmap.md](development-roadmap.md)를 따른다. WebSocket을 온라인 통신 후보로 우선 검토하되 서버 운영 방식·라이브러리·배포·프로토콜은 아직 확정하지 않았다.

## 역할과 기준

- 프로젝트 담당자: 게임 기획, React 화면과 공통 UI, 게임 규칙 모듈과 최종 통합 방향을 주도한다. 규칙 변경과 공개 인터페이스는 동료와 상의해 결정한다.
- 온라인 담당 동료: 방 생성·참가, WebSocket 연결, 세션·상태 전달, 재접속과 서버 실행·배포 방안을 조사·구현한다. 게임 규칙은 별도로 재구현하지 않고 합의된 규칙 모듈을 호출한다.
- 공통 계약(게임 명령, 응답, 오류와 플레이어에게 보이는 상태)은 양쪽이 함께 검토한다. 기존 UI나 규칙 모델을 동의 없이 갈아엎지 않고, 필요한 변경은 이유와 영향 범위를 공유한다.
- 변경은 기능 브랜치에서 진행하고 PR로 합친다. 같은 파일을 동시에 편집해야 하면 먼저 조율한다. 로컬 미커밋 파일은 다른 사람이나 별도 worktree에 자동으로 전달되지 않는다. 공유할 기준 버전은 커밋과 PR 또는 명시된 커밋 SHA로 맞춘다.

## 권장 구조

```text
React 화면 → 세션 인터페이스 → 로컬 세션 또는 온라인 클라이언트
                                           ↕ WebSocket
                              온라인 세션 / 신뢰 가능한 서버
                                           ↓
                               공통 TypeScript 게임 규칙
```

WebSocket은 브라우저와 서버 사이의 양방향 통신 수단이다. 연결을 받아 게임 상태를 관리할 서버 또는 관리형 실행 환경은 필요하다. 직접 서버 운영을 최소화하려는 방향을 유지하며, 호스팅·상시 연결 지원·비용은 비교 후 결정한다. 특정 서버 프레임워크, DB, WebSocket 라이브러리나 호스팅은 지금 확정하지 않는다. 순수 규칙 코드의 실제 공유 방식도 저장소 구조와 실행 환경을 확인해 합의한다.

서버는 클라이언트가 보내는 판 전체를 정답으로 믿지 않는다. 로그인 또는 임시 세션을 확인하고 해당 연결의 플레이어 ID를 서버가 정한 뒤, 행동 권한과 규칙을 검증해 상태를 갱신한다. 성공한 결과 중 각 플레이어가 볼 수 있는 정보만 전달한다. 상대의 손패·지뢰·은신 정보와 난수 상태를 감춰서 UI에 표시하지 않는 것만으로는 부족하며, 네트워크 응답 자체에서 제외한다.

## 통신 계약 초안 — 합의 전 예시

메시지 이름·필드는 확정 사양이 아니라 양쪽이 함께 결정할 출발점이다.

| 방향 | 용도 | 예시 정보 |
| --- | --- | --- |
| 클라이언트 → 서버 | 방 참가 또는 재접속 | 방 식별자, 인증·재접속 수단 |
| 클라이언트 → 서버 | 행동 요청 | 요청 ID, 기준 상태 버전, 행동 종류와 좌표 등 입력 |
| 서버 → 요청자 | 수락·거부 | 요청 ID, 결과 또는 오류 코드, 현재 버전 |
| 서버 → 참가자 | 상태 동기화 | 상태 버전과 해당 플레이어에게 허용된 화면용 상태 |
| 서버 → 참가자 | 연결·방·게임 상태 | 참가·퇴장, 연결 끊김, 게임 시작·종료 등 |

동작 예: A가 착수를 요청하면 서버는 세션의 A 신원과 방 참가 여부를 확인하고, 중복 요청과 상태 버전을 검사한 뒤 공통 규칙 모듈에 명령을 전달한다. 승인 시 상태를 원자적으로 갱신하고 각 플레이어에게 허용된 상태를 보낸다. 거부하면 상태를 변경하지 않고 요청자에게 이유를 알린다. 방어 응답 중인지는 확정될 규칙에 따라 같은 방식으로 검증한다.

- 중복 요청 ID와 상태 갱신을 일관되게 처리하고, 중복 재전송 시 같은 결과를 돌려준다. 충돌·오래된 버전은 거부하고 최신 허용 상태를 다시 받을 수 있게 설계한다.
- 각 방에서 명령을 직렬화하거나 동등한 동시성 제어를 적용한다. 서버 재시작 후 재접속과 중복 처리를 보장할지에 따라 저장 방식과 수명을 결정한다.
- 메시지 버전, 오류 코드, 재접속 신원 확인·기존 연결 처리, 방 수명, 연결 감지, 방어 응답 시간 초과는 합의 사항이다. 재접속 키·토큰은 로그나 저장소에 남기지 않는다.
- 실제 서비스는 WSS를 사용하고 서버에서 Origin 확인, 인증·방 권한, 메시지 검증, 크기·요청 빈도 제한을 적용한다. 연결 성공만으로 개별 행동 권한을 부여하지 않는다.

## 착수 시점과 단계

1. **지금, 1단계 설계와 병행:** 동료는 위 문서와 규칙 모델을 읽고 WebSocket 호스팅 후보, 연결 유지·비용, 서버 실행 방식과 메시지 계약 초안을 조사한다. 기본 대국과 미정인 효과의 범위는 게임 기획을 따른다.
2. **2단계 로컬 기본 게임을 만드는 동안:** 최소한의 임시 서버로 두 테스트 클라이언트의 연결·방 참가·메시지 교환을 검증할 수 있다. 실제 게임 규칙과 무관한 테스트 데이터로 진행하고 실서비스 인증·보안이 완료됐다고 간주하지 않는다.
3. **2단계의 상태·명령 인터페이스와 기본 게임이 검증되면:** 작은 온라인 수직 단면을 시작한다. 방 참가 → 두 클라이언트의 기본 착수 → 서버 검증·상태 반영 → 끊김 후 상태 복원을 우선 연결한다. 그다음 동시·중복 요청을 검증한다. 2단계 전체 화면 완성을 기다릴 필요는 없지만 계약은 양쪽이 합의해야 한다.
4. **3~4단계의 방어·카드 규칙이 확정되면:** 응답 대기, 시간 초과, 플레이어별 숨김 정보를 온라인에서 구현·검증한다. 5단계에서 실제 호스팅, 인증·권한, 장애·재접속 및 전체 2인 플레이를 통합한다.

날짜는 작업 속도와 기획 결정에 달려 있으므로 정하지 않는다. 온라인은 마지막 단계까지 기다리지 않고 일찍 연결 위험을 검증하되, 모든 카드와 온라인 운영을 한 번에 완성하려 하지 않는다.

## 동료에게 전달할 요청

> 현재 게임의 기획·규칙·UI 방향은 이 저장소를 기준으로 함께 진행하고 싶어. `docs/game-spec.md`, `docs/game-rules-design.md`, `docs/online-collaboration.md`를 읽고, 우선 WebSocket 기반 방 참가·통신과 재접속의 기술 선택지, 서버가 관리할 상태, 메시지 계약 초안을 제안해줘. 게임 규칙은 중복 구현하지 말고 공통 TypeScript 규칙을 서버에서 호출할 수 있는 경계를 함께 정하자. 손패·지뢰 등 비공개 정보는 서버가 플레이어별로 걸러 보내야 해. 첫 단계에서는 임시 연결 실험까지 진행하고, 라이브러리·호스팅·DB와 확정되지 않은 게임 규칙을 정하기 전에 선택지와 영향을 공유해줘. 기능 브랜치에서 작업하고 완료 내용과 질문을 PR에 남겨줘.

## 통합 확인

- 두 플레이어가 서로 다른 기기나 독립 브라우저에서 같은 방의 공개 판과 턴을 동일하게 본다.
- 잘못된 턴·좌표, 중복·동시·오래된 요청을 거부하거나 중복 적용하지 않는다.
- 끊김·재접속 중 최신 상태를 복구하고 카드·턴 시작 지급이 중복되지 않는다.
- 상대에게 허용되지 않은 손패·지뢰·은신·난수 정보가 메시지와 재접속 응답에 없다.
- 공격 후 방어 응답, 미응답·접속 종료 시 처리는 확정된 기획에 맞게 동작한다.
- 검증 범위와 남은 위험을 PR과 작업 기록에 남긴다.
